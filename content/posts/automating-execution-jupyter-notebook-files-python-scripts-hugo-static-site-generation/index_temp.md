## Motivation

The primary motivation for automation came from several realizations:

1. Setting directory variables would avoid any issues with managing where the static files were stored locally
2. I wanted to be able to pull updated data, execute Jupyter notebooks, and update the posts within my Hugo site without manual intervention
3. I like to include the HTML and PDF exports of the Jupyter notebooks, which required copying the exports into the static files of the website
4. I needed a system to build the "index.md" files that are present in each post directory, and automatically include Python code and functions (again, without copying/pasting or manual processes)

## How doit Works

If you have used `make`, `doit` will feel familiar: you declare tasks, you declare what each task depends on and what it produces, and the tool works out what actually needs to run. The difference is that everything is plain Python rather than a separate makefile syntax.

A task is any function in `dodo.py` whose name begins with `task_`. The function returns a dictionary describing the work, and the keys that matter here are:

* `actions` — what to run. Either a shell command as a string, or a Python callable.
* `file_dep` — the files the task reads. If none of them have changed, the task is skipped.
* `targets` — the files the task writes. If a target is missing, the task runs.
* `task_dep` — other tasks that must run first, used when the ordering is not implied by files alone.
* `uptodate` — a custom check that returns `True` when the task can be skipped, for cases where file timestamps are not the right signal.
* `verbosity` — `2` lets the task's own output through to the terminal, which is what makes the print statements below visible.

The one piece of `doit` behavior worth knowing before reading any further is that a task function can `yield` several dictionaries instead of returning one. Each becomes an independent sub-task with its own name and its own dependencies. That is what makes the per-post tasks possible: rather than one task that loops over every post directory, there is one sub-task *per* post directory, so a change to a single notebook only re-runs that notebook.

## The Pipeline

The tasks below run in this order, each one depending on the last:

1. `config` — create the content, pages, posts, and public directories if they don't exist
2. `list_posts_subdirs` — enumerate the post directories
3. `run_post_notebooks` — execute any notebook whose contents have changed
4. `export_post_notebooks` — convert each notebook to HTML, PDF, and Markdown
5. `build_post_indices` — assemble the `index.md` for each post
6. `clean_public` — delete the previous Hugo output
7. `build_site` — run `hugo`
8. `copy_notebook_exports` — copy the notebook HTML exports into `static/posts/<slug>/`
9. `copy_projects_research_exports` — copy the research HTML into `static/projects-research/`
10. `create_schwab_callback` — write the Schwab OAuth callback page

The `task_build_post_indices` function builds the `index.md` file within each "post" directory. There are two ways a post can be assembled, and the task branches on whichever marker file it finds in the directory:

* **Template-driven posts** have an `index_temp.md` file. This is a hand-written template containing the Hugo front matter, the prose, and a set of `<!-- INSERT_<name>_HERE -->` placeholder comments. Alongside it, an `index_dep.txt` file lists the markdown snippets that fill those placeholders. `build_index.py` does the substitution.
* **Notebook-driven posts** have a `frontmatter.md` file, which holds nothing but the Hugo front matter. The body of the post is the Markdown export of the notebook produced by `task_export_post_notebooks` above, and the two are simply concatenated.

Notebook-driven posts are what I use for most quantitative writing now, since it means the post and the analysis are the same file and cannot fall out of sync. Template-driven posts are still useful when the prose dominates and I only want to pull a few computed tables or figures into it — this post is one of them.

<!-- INSERT_09_task_build_post_indices_HERE -->

Note that the notebook-driven branch appends a `## Code` heading and a `post-files` shortcode to the end of every generated `index.md`. That shortcode is what renders the links to the `.ipynb`, `.html`, and `.pdf` exports at the bottom of each post, and it builds those links from the `slug` in the front matter — so the slug has to match the actual filenames in the post directory.

The two branches are not mutually exclusive in the code, so a directory containing both an `index_temp.md` and a `frontmatter.md` would yield two tasks writing the same `index.md`. In practice each post uses one or the other.

The `task_copy_notebook_exports` function copies the HTML exports generated above into `static/posts/<slug>/`, where Hugo will pick them up as static assets.

The reason for the extra copy is that the exports live next to the content they were generated from, inside each post directory. Hugo would otherwise treat those `.html` files as pages in their own right, so my `hugo.toml` sets:

```toml
ignoreFiles = ['\.html$']
```

That keeps the exports from being rendered as pages, but it also means they never reach the built site on their own — hence copying them into `static/`. (As of Hugo v0.158+, `security.allowContent` blocks `text/html` content as well.)

One consequence worth knowing about: this task runs *after* `task_build_site`, so it writes into `static/` when Hugo has already copied `static/` into `public/`. A brand new notebook export therefore does not appear on the site until the *next* run. When adding a post, run `doit` twice.

## Executing doit

To execute `doit`, simply run:

    $ doit

in the terminal after changing to the high level directory.

Alternatively, you can list the individual tasks with:

    $ doit list

and then execute individually, such as:

    $ doit build_post_indices

And finally, `doit` can be forced to execute all tasks with:

    $ doit --always-execute

or an individual task with:

    $ doit --always-execute build_post_indices
