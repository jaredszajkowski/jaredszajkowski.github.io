     Plan: Extract all session data and build a GPX for one workout

     Context

     The Oura export contains a workout log (workout.csv) plus ~60 other CSVs of
     sensor streams and daily summaries. We want a script that, given one
     workout's
     UUID, pulls together everything recorded for that session from every file
     and emits a GPX track (openable in Strava, Garmin Connect, etc.), plus a
     companion data dump.

     Two facts discovered during exploration shape the whole design:

     1. GPS data exists in data/App Data/rawlocation.csv (78k rows:
     latitude, longitude, altitude, timestamp, UTC Z). This is the only source
     of coordinates, so it is what the GPX track is built from. Verified: a real
     running workout yielded 297 trackpoints, all with altitude.
     2. There is no ID linking rows across files. rawlocation.csv and the
     sensor streams have no workout/session id, and
     workoutheartratesession.selected_activity_id does not match any
     workout.csv id (verified). Therefore linking is time-based: filter each
     file to rows overlapping the workout's [start_datetime, end_datetime]
     window. An id match is still attempted where an id-type column exists.

     Timezone gotcha (verified): workout.csv timestamps carry a local offset
     (e.g. ...-05:00); rawlocation/heartrate/etc. are UTC (...Z). Everything
     must be normalized to timezone-aware UTC before comparing, or the window is
     off
     by the offset.

     Coverage caveat: the location stream starts ~2025-04-16; indoor workouts
     and
     anything earlier have no GPS. Per the user's choice, the script warns and 
     skips
     the GPX in that case but still writes the sidecars.

     Deliverables

     A single new script (no deps beyond the Python stdlib):
     extract_session.py in the repo root.

     Usage:
     python3 extract_session.py <workout_id> [--outdir sessions]

     Outputs (non-destructive — written under a new sessions/<workout_id>/,
     never
     into data/):
     - <workout_id>.gpx  — enriched GPS track (skipped with a warning if no GPS)
     - <workout_id>.json — machine-readable dump of the workout row + per-file
     matches
     - <workout_id>.md   — human-readable report of the same

     GPX design (Track + all sensors)

     - One <trk> / <trkseg>; each rawlocation row in the window becomes a
     <trkpt lat lon> with <ele> (altitude) and <time> (UTC).
     - Namespaces: GPX 1.1 + Garmin TrackPointExtension (gpxtpx) so consumers
     read the sensors. Per trackpoint, attach nearest-in-time sample from each
     stream, only if within a tolerance (default ±30 s) so gaps aren't bridged
     with stale values:
       - gpxtpx:hr   ← heartrate.csv (bpm)
       - gpxtpx:cad  ← stepcount.csv — steps in the bucket containing the point,
     converted to steps/min (document this; Oura has no true cadence)
       - gpxtpx:atemp← temperature.csv (skin_temp; note in output that it is
     skin, not ambient, temperature)
       - speed/course are available directly on the rawlocation row; include
     <gpxtpx:speed> when present (non-fatal if a consumer ignores it).
     - <metadata> carries the workout id, activity, and local start time; <trk>
     <name> = activity + date.

     Time-join core (reused everywhere)

     Helpers:
     - parse_ts(s) → aware datetime in UTC. Handles ...Z and numeric offsets via
     datetime.fromisoformat (replace trailing Z with +00:00); treat a
     tz-naive value as UTC and note it.
     - in_window(ts, start, end) and overlaps(a_start, a_end, start, end).
     - nearest(sorted_samples, t, tol) for enrichment (bisect on prebuilt,
     time-sorted lists loaded once for the window).

     Large files (heartrate 574k, temperature 680k, motion 763k, stepcount
     357k, rawlocation 78k, motion 41 MB, …) are streamed with csv.reader
     (delimiter ;), keeping only rows in the window — never loaded whole.

     Sidecar dump: generic per-file scan

     Loop over every *.csv in data/App Data/. Introspect the header once and
     pick
     a strategy (no per-file hardcoding of all 61 files):

     1. ID match — if a column is id/*_id/*_identifier, collect rows whose
     value equals the workout id (covers any future direct link; today matches
     only workout.csv itself, plus a checked-but-usually-empty
     vo2maxworkoutestimate.workout_identifier).
     2. Point-in-window — header has a lone timestamp: keep rows with
     timestamp in the window. (heartrate, temperature, motion, stepcount,
     importedstepcount, daytimestress, ringbatterylevel, rawlocation,
     workoutpacedistance, …)
     3. Interval overlap — header has a start/end pair
     (start_datetime/end_datetime, start_time/end_time,
     bedtime_start/bedtime_end): keep rows whose interval overlaps the window.
     (workoutheartratesession, activitypredictionsegment, enhancedtag,
     restmodeperiod, meal, sleepmodel, …)
     4. Day match — header has day but no usable timestamp: keep rows where
     day == workout's day. (dailyactivity, dailyreadiness, dailysleep,
     dailyresilience, dailyspo2, dailystress, dailycardiovascular*, sleeptime,
     …)

     For each file record: filename, strategy used, match count, and — for
     numeric
     columns — min/max/mean plus first/last timestamp. Store full rows when the
     match
     is small (≤ a cap, e.g. 50); otherwise store the summary + first/last rows
     to
     keep the JSON/MD manageable. Files with 0 matches are listed as "no data"
     (the
     ~30 empty CSVs fall out here naturally). contributors-style embedded-JSON
     columns (in the daily files) are json.loads-parsed for the report.

     Edge cases

     - Workout id not found in workout.csv → error, exit non-zero, list a few
     valid ids.
     - No GPS points in window → warn, skip .gpx, still write .json/.md
     (user's choice).
     - Sensor gaps → enrichment simply omits a tag when no sample is within
     tolerance; trackpoint still emitted with position/time.
     - LibreOffice lock (.~lock.workout.csv# seen) is read-only noise; the
     script only reads, so it's unaffected.
     - Empty/near-empty CSVs handled by the generic scan (0 matches).

     Files

     - New: extract_session.py (repo root).
     - Read-only inputs: all of data/App Data/*.csv — primary: workout.csv,
     rawlocation.csv, heartrate.csv, stepcount.csv, temperature.csv.
     - New outputs: sessions/<id>/<id>.{gpx,json,md}.

  from memory.

  Read 1 file, ran 1 shell command (ctrl+o to expand)

● Cadence is derived, not measured — the Oura ring has no cadence sensor. It's
  computed from the stepcount.csv stream. Here's the full pipeline:

  1. Source data — stepcount.csv buckets
  Each row is a time bucket: timestamp (ISO start), end_time (Unix epoch
  milliseconds), and steps (a float — Oura reports fractional steps). In your
  data these buckets are 1 minute long with ~150 steps each during a run.

  2. Rate calculation (load_cadence_series, extract_session.py:242)
  For every bucket that overlaps the workout window:
  secs = (end_time − timestamp)          # ~60 s
  cadence = steps / secs × 60            # → steps per minute
  The value is anchored at the bucket's midpoint in time. Because it divides by
  the bucket's actual duration, the rate is correct even if a bucket only
  partially overlaps the workout edges (that's why you saw a min=4 — a boundary
  bucket that was mostly outside the run).

  3. Attaching to each GPS point (build_gpx, extract_session.py:369)
  Each trackpoint takes the nearest bucket midpoint within a ±90 s tolerance
  (wider than the ±30 s used for HR, because the buckets are coarse). So every
  trackpoint in a given minute gets that minute's average step rate.

  Two things to be aware of:

  - It's a per-minute average, not instantaneous. All the GPS points within a
  minute share one cadence number, so it's smoother/blockier than a real cadence
  sensor's output.
  - Units convention — this is the important one. The value is total steps per 
  minute (~150 for your run). Some running platforms interpret gpxtpx:cad as
  one-foot cadence / RPM (~75–90, the "stride rate" convention). Garmin Connect
  and Strava generally treat this field as full steps/min, so ~150 will display
  correctly there — but if a tool shows your cadence at ~2× or ~½× what you
  expect, that's the steps-vs-strides mismatch, and I'd halve the value before
  writing the tag.

  Do you want me to keep it as steps/min, or switch to the one-foot (÷2)
  convention some devices expect?
